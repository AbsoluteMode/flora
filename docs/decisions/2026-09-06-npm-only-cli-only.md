# Один канал установки и один вид исполнителя

## Контекст

К v0.2.1 у флоры появились два пути, которых не было в первом выпуске: нативные установщики
(`.exe` через Inno Setup, `.pkg`, архивы с `install.sh`, каждый со своей копией Node) и путь `external` —
шаг, который не запускает CLI, а ждёт, пока его заберёт через MCP уже открытый GUI-агент (Codex app,
Claude Desktop), с очередью заявок, токенами claim и heartbeat.

Оба работали: установщики собирались и проверялись на пяти раннерах, GUI-путь прошёл живую проверку
в обоих приложениях. Но оба удваивали то, что уже есть. Установщик тащит второй Node ради пакета,
который ставится одной командой npm; GUI-путь держит вторую машину состояний рядом с движком ради
исполнителя, который флора не контролирует и не может ограничить в инструментах.

## Решение

Флора распространяется только как npm-пакет: `npm install -g @absolutemode/flora` или тот же тарбол с
релиза. Исполнитель шага — только то, что флора запускает сама на этой машине: `claude-code`, `codex`,
`harmonia`, `command` и явно настроенный `api`. Харнесс `external`, очередь `src/bridge`, фоновые
прогоны в MCP-сервере (`start_workflow`, `claim_step` и остальные), `installers/`, `scripts/` сборки
дистрибутивов и матрица CI под них убраны.

Остаётся `flora connect`: он печатает настройки MCP для агента, который *пишет и запускает* воркфлоу
через `flora mcp`. Это авторинг, а не исполнение чужими руками, и он был в v0.1.0.

## Почему

Инструмент делает одну вещь: даёт харнессу контракт. Каждый лишний способ поставить или исполнить —
это отдельная документация, отдельные тесты и отдельный класс ошибок, которые не про контракт.
Версия 0.3.0, потому что публичная поверхность уменьшилась.
