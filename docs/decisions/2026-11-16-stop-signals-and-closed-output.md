# Остановка сигналом и закрытый вывод

## Контекст

16.11.2026, разбор «что во Флоре можно улучшить наверняка». Два дефекта воспроизведены на установленной
0.6.2 прогоном из одного командного шага (`echo started; sleep 177`):

- **SIGTERM и SIGHUP.** Процесс flora умирал сразу, процессы шага продолжали работать, в журнале прогон
  оставался `running` (читатели показывали `interrupted` только через 90 с). SIGINT при этом работал
  правильно. Причина: `commandRun`, `startViewer` и `commandWatch` подписывались только на SIGINT, а шаг
  запускается в собственной группе процессов (`adapters/command.ts`, `detached`), поэтому смерть flora его
  не задевает. Так завершают процесс `kill`, launchd и закрытый терминал. Тот же риск 12.11 отмечен в ревью
  потребителя Флоры (перезапуск ядра посреди прогона) — там по чтению кода, без живого прогона.
- **Закрытый вывод.** Когда читатель stdout исчезал посреди прогона, flora выходила с кодом 0 при записи
  `running` в журнале. Причина: `tolerateClosedStdout` делал `process.exit(0)` на EPIPE для всех команд,
  хотя задуман был для `flora runs --json | head`.

## Решение

1. **Одна остановка на три сигнала** (`onStopSignal` в `src/cli.ts`). SIGINT, SIGTERM и SIGHUP запускают
   один и тот же путь: `run` прерывает прогон (дерево шага убивается, в журнал пишется итог `error`, код
   выхода 1), `serve`/`open` закрывают сервер, `watch` ждёт прогоны в работе.
2. **Предел ожидания.** Повторный сигнал или 10 секунд без завершения — выход с кодом 128 + номер сигнала.
   Для `watch` предела по времени нет: ждать прогоны там и есть смысл остановки, второй сигнал выходит сразу.
3. **Закрытый вывод не останавливает работу.** Для `run`, `watch`, `serve`, `open` EPIPE на stdout и stderr
   молча проглатывается: прогон доходит до настоящего итога, и код выхода отражает его. Остальные команды
   выходят с 0, как раньше; `mcp` тоже — там stdout и есть канал протокола.

## Почему

- Сигнал от супервизора — штатный способ остановки, а не авария. Без обработки каждый перезапуск сервиса
  оставлял исполнителя с полными правами работать без таймаута и без записи в журнале.
- Код выхода 0 при незавершённом прогоне — ложь вызывающему. Исчезнувший читатель ничего не говорит о
  работе, поэтому правильное поведение — доделать и записать итог.
- Предел ожидания нужен, потому что перехваченный SIGTERM больше не завершает процесс сам: зависшая уборка
  сделала бы flora неубиваемой для всего, кроме SIGKILL.

## Что протестировали

- `src/__tests__/stop-signals.test.ts` — на настоящих процессах, 7 сценариев. На коде до правки падают 5:
  SIGTERM, SIGHUP, повторный сигнал, успешный и упавший прогон при закрытом выводе. SIGINT и листинг в
  закрытый канал проходили и раньше — это контроль от регрессии.
- Вручную: шаг, породивший процесс в отдельной сессии с унаследованным stdout. Уборка не завершается (вывод
  шага держит чужой процесс), flora выходит по пределу через 10 с с кодом 143, прогон в журнале остаётся
  `running` и становится `interrupted` по сердцебиению. Процесс в отдельной сессии переживает остановку —
  дотянуться до него по группе нельзя. До правки в этом случае flora после ctrl-c висела бессрочно.

## Отвергли

- Менять `exit(0)` на `exit(1)` при EPIPE — работа всё равно брошена, шаг остаётся сиротой.
- Прерывать прогон при закрытом выводе — потеря читателя не причина бросать сделанное наполовину.
- Не запускать шаг в отдельной группе — тогда нельзя убить дерево шага по таймауту целиком.
- WAL для журнала — предлагалось в ревью, но сбой чтения 12.11 был у потребителя без своего таймаута;
  пользы для самой Флоры не показано.
