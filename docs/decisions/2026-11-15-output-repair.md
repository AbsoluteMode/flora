# Исправление формы вывода вместо провала шага

## Контекст

15.11.2026 шаг с исполнителем Codex сделал работу и вернул итог, но поля `changes` и `checks` пришли
списками строк, а схема вывода шага объявляла их строками. Флора пометила шаг упавшим: «output does not
match the schema: /changes must be string; /checks must be string». Прогон стал красным, хотя работа была
сделана. Вопрос владельца: почему флора не сообщила агенту, что формат не соблюдён?

Почему агент вернул не ту форму — по коду 0.6.1, без догадок:

- **Схема до агента не доходила вообще.** `withOutputInstruction` (`src/output.ts`) дописывал к промпту
  только «закончи ответ одним блоком ```json» — без самой схемы. Ни один адаптер не передавал схему и
  нативно: у `codex exec` нет `--output-schema`, у `claude -p` нет `--json-schema`, у `agy` — ничего. Codex
  видел только текст задачи автора и угадывал форму сам; списки для «изменений» и «проверок» — разумная
  догадка.
- Проверка шла по правильной схеме (`readOutput` берёт `body.output.schema` того же шага), строгий режим
  ничего молча не отбрасывал — его просто не было.
- Несоответствие схемы сразу роняло шаг: `runBody` → `readOutput` → `outputError`, `status: failed`.
  Единственный путь дать агенту второй шанс — `on_fail.retry`, а он перезапускает работу целиком.

## Решение

1. **Схема в промпте.** Если у контракта есть `schema`, к инструкции про блок ```json дописывается сама
   схема («must match this JSON Schema, including the type of every field»). Для всех агентных исполнителей
   одинаково: claude-code, codex, antigravity, harmonia, api.
2. **Исправление формы (`output_repair`).** Если агент закончил работу (exit 0), а ответ не прошёл контракт
   (не JSON, нет блока, пусто, не по схеме), флора не роняет шаг, а возвращается к тому же агенту:
   - `resume` — в ту же сессию, если адаптер умеет её продолжать и id известен: claude-code
     `claude -p --resume <session_id>`, codex `codex exec … resume <thread_id>`, antigravity
     `agy --conversation <conversation_id>`. Id адаптеры теперь достают из своих потоков (`session_id`,
     `thread.started.thread_id`, `conversation_id`) и кладут в `Evidence.sessionId`;
   - `fresh` — иначе (harmonia, api, неизвестный id, сессию не удалось продолжить): один короткий новый
     запрос тем же исполнителем, в нём цитата невалидного ответа (хвост до 32 КБ), ошибки и схема.
   Сообщение на английском: ошибки как есть (JSON pointer и причина), схема, «Do not redo the work, do not
   change files and do not run commands; return the same result in the required form.»
3. **Права не шире шага.** Repair-запрос всегда без инструментов: claude — `--strict-mcp-config` без
   `--mcp-config` и `--disallowedTools Bash,Edit,Write,MultiEdit,NotebookEdit`; codex — `--sandbox
   read-only`, из `executor.args` выкинуты `--full-auto`, `--dangerously-bypass-approvals-and-sandbox`,
   `--yolo`, `-s/--sandbox`, личные MCP-серверы выключены, контрактные не монтируются; antigravity —
   read-настройки без `--mode` даже у `access: write`. Fallback через `execute` (harmonia, api) идёт с теми же
   правами, что у шага, и без MCP.
4. **Настройка.** `output_repair: { attempts, timeout_min }` — в корне workflow (умолчание для всех агентных
   шагов), на шаге, на parallel-шаге (для веток) и на ветке. `attempts` по умолчанию 2, `0` — прежнее
   поведение. `fresh` пробуется один раз, сколько бы ни было `attempts`. На `command`-шаге и на шаге без
   `output.type: json` настройку отклоняет валидатор (и JSON Schema контракта) — молча игнорируемая
   настройка в этом репозитории запрещена.
5. **Таймаут.** У каждого repair-запроса свой короткий wall-clock: `timeout_min` (по умолчанию 5), но не
   больше `executor.timeout_min` шага; `0` с одной стороны оставляет лимит другой. `stall_min` — шага.
   Таймаут или отмена прогона прекращают исправления сразу.
6. **Журнал и учёт.** События `output_repair_start` и `output_repair_result` (добавлены, старые не тронуты),
   на шаге — `StepResult.outputRepairs[]`. Время, токены и деньги repair-запросов прибавляются к
   `evidence` шага, поэтому `flora usage`, отчёт и аналитика считают их без изменений. `evidence.output`
   остаётся ответом работы; ответ каждого исправления — в `outputRepairs[i].output`.
7. **Исчерпали** — шаг падает как раньше, `outputError` = последняя причина + «(output repair: N requests did
   not fix it[; the last one failed: …])». Дальше обычный `on_fail.retry`, если он есть.

## Почему

- Работа агента дорогая (минуты и доллары), форма ответа — дешёвая. Ронять шаг из-за формы значит
  выбрасывать сделанное; `on_fail.retry` переделывает всё заново и может дать другой результат.
- Та же сессия — у агента весь контекст сделанного, он переписывает свой же итог, а не пересказывает
  чужой. Fresh-запрос — честный запасной путь: преобразование цитаты, а не работа.
- Схема — контракт автора workflow. Агенту её нужно показать заранее (п. 1) и сказать, где он её нарушил
  (п. 2), а не исправлять за него.
- Свой короткий таймаут вместо «общего на шаг»: исправление формы занимает секунды, и зависшая повторная
  сессия не должна съедать оставшиеся 15 минут шага; общий бюджет шага при этом не растягивается больше,
  чем на `attempts × timeout_min`.
- Нативная передача схемы (`codex exec --output-schema`, `claude -p --json-schema`) **отложена**: строгий
  режим OpenAI требует `additionalProperties: false` и все поля в `required` — обычная схема автора
  (как в живом случае: `required` не на все поля) отвергается API, и шаг падает до работы. Проверить флаги
  и поведение без живых CLI здесь нельзя (запуск запрещён), а текст в промпте работает у всех исполнителей
  одинаково и проверяется тестами.

## Что протестировали

Только подменными исполнителями и CLI-двойниками, настоящие `claude`/`codex`/`agy` не запускались.

- Живой случай: списки вместо строк → одно исправление в той же сессии → шаг прошёл, работа не
  перезапускалась (`execute` один раз, `repair` один раз с тем же id), события и сумма денег/токенов/времени.
- Сообщение агенту: пути и причины, схема, просьба не переделывать работу; в `resume` ответ не цитируется.
- Две неудачи → `failed`, в ошибке число попыток и последняя причина; второй запрос — про то, что осталось.
- `attempts: 0` → прежний текст ошибки, ни одного вызова; умолчание workflow и перекрытие шагом.
- Не JSON, битый JSON, пустой ответ → исправление; больше 256 КБ и упавший исполнитель → нет.
- `command`-шаг не исправляется; ветка parallel-шага — с `branch` в событиях.
- Адаптер без repair → один fresh-запрос через `execute` без MCP и без двойной инструкции; resumable без
  id → fresh; не удалось продолжить сессию → один fresh; длинный ответ цитируется хвостом.
- Таймаут: адаптер получает `timeout_min` исправления и `stall_min` шага, после таймаута попыток нет.
  Отмена прогона во время исправления — запрос остановлен, прогон `error`.
- Через настоящие адаптеры с двойниками `claude`, `codex`, `agy`: схема в промпте работы, точные аргументы
  продолжения сессии (`--resume`, `exec … resume <id>`, `--conversation`), read-only, одна инструкция в
  repair-сообщении, `Evidence.sessionId`; запись в журнал через recorder и `RunStore`.
- Валидатор и JSON Schema контракта одинаково отклоняют плохие `output_repair`.

Не проверено без живых CLI: что `codex exec resume` принимает `--sandbox`/`-c`/`--model` перед
подкомандой и держит read-only на продолжении; что `claude -p --resume` в текущей версии продолжает
сессию, а не форкает (на результат не влияет — id берётся из ответа); что `agy --conversation` в print-режиме
продолжает тот же разговор.

## Отвергли

- **Сразу ронять шаг (как в 0.6.1)** — выбрасывает сделанную работу из-за формы ответа; остаётся как
  `attempts: 0`.
- **Молча приводить типы внутри флоры** (список → строка и т. п.) — схема — контракт автора; приведение
  подменяет его догадкой флоры. Нужна гибкость — автор объявляет `anyOf` в схеме.
- **Перезапускать шаг целиком** — это `on_fail.retry`: дорого, повторяет побочные эффекты и может дать
  другой результат. Остаётся следующим рубежом после исчерпанных исправлений.
- **Общий таймаут шага на работу и исправления** — зависшее продолжение съело бы остаток бюджета работы;
  выбран свой короткий лимит с потолком `executor.timeout_min`.
